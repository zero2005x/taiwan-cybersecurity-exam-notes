# 114 年高考三級資通安全：資通安全防護技術

查核日：2026-10-10。[阿摩試卷 128301](https://yamol.tw/exam/128301)與[重複收錄 128514](https://yamol.tw/exam/128514)。原試卷四大題，阿摩拆為六小題。128301 六小題各一份網友詳解、申論作答均為 0；128514 六小題均顯示詳解 0。網友內容為署名摘要，下面完整答案由整理者補寫。

## 一、五種電子郵件安全技術及功能（25 分）

**最佳一份**：Aaron Lim，2025-07-11，essay-546843，詳解 6534534，評價 2／0，全文可讀。

**網友摘要**：以郵件內容簽章與加密、網域寄件授權、DKIM、DMARC 及 STARTTLS 分層防護。

**查核及修正**：DMARC 不是 SPF 或 DKIM 任一失敗便拒收；至少一種驗證通過且與可見寄件者網域對齊，即可通過 DMARC。SPF 不直接驗證顯示名稱，DKIM 是簽章而非加密；機會式 STARTTLS 仍可能遭降級，不能保證抵抗中間人。

**整理者完整作答，考試當時**：

| 技術 | 機制與功能 | 限制及搭配 |
|---|---|---|
| SPF | 網域透過 DNS 公告授權寄件主機，收件端比對連線 IP 與 SMTP envelope 寄件網域，降低冒用該網域寄信 | 不保護內容，不直接驗證使用者看到的 From；轉寄可能影響結果 |
| DKIM | 寄件系統用網域私鑰簽署指定標頭與本文，收件端查 DNS 公鑰驗證，確認簽署網域及被簽資料完整性 | 簽署網域未必等於可見 From；不是個人身分保證，也不加密內容 |
| DMARC | 以可見 From 網域為中心，檢查 SPF 或 DKIM 是否通過且網域對齊，並發布 none、quarantine、reject 等處理政策與報告要求 | 不能阻止相似拼字網域、冒用顯示名稱或已被入侵的合法帳號；收件端依自身政策處置 |
| S/MIME | 透過 MIME 密碼封裝及憑證提供訊息簽章與加密；簽章支援來源鑑別、完整性與不可否認性，加密保護內容 | 收發端須支援並管理憑證、私鑰與信賴鏈；只有簽章不提供機密性 |
| SMTP STARTTLS | 將 SMTP 連線升級為 TLS，保護兩個郵件節點間傳輸，減少途中竊聽及竄改 | 是逐跳傳輸保護，不是端到端內容加密；須適當憑證驗證及強制傳輸政策，避免降級 |

例如 From 是公司網域，即使 SPF 因轉寄失敗，只要合法公司 DKIM 簽章驗證成功且對齊，仍可通過 DMARC；兩者都無對齊的通過結果才不能通過。此例是整理者說明。郵件防護還需釣魚辨識、惡意附件檢查及帳號保護，上述五項不是所有威脅的完整解方。

**現行差異**：114 年考試可引用 RFC 7489。2026 年 RFC Editor 已將它標為被 RFC 9989、9990、9991 取代，分別處理 DMARC 本體及報告；此更新列於現行補充，不套回考試年份。

**官方標準**：[SPF，RFC 7208](https://www.rfc-editor.org/info/rfc7208/)；[DKIM，RFC 6376](https://www.rfc-editor.org/info/rfc6376/)；[考試時 DMARC，RFC 7489](https://www.rfc-editor.org/info/rfc7489/)；[S/MIME 4.0，RFC 8551](https://www.rfc-editor.org/info/rfc8551/)；[STARTTLS，RFC 3207 第 6 節](https://www.rfc-editor.org/info/rfc3207/)；[現行 DMARC，RFC 9989](https://www.rfc-editor.org/info/rfc9989/)。

## 二、滲透測試、紅隊演練與 BAS 比較（25 分）

**最佳一份**：Aaron Lim，2025-07-11，essay-546844，詳解 6534538，評價 0／0，全文可讀。

**網友摘要**：滲透測試驗證可利用弱點，紅隊模擬攻擊者行動，BAS 以自動化方式反覆測試安全控制。

**查核及修正**：將滲透測試固定比喻為 DFS、紅隊固定比喻為 BFS 不構成業界定義。滲透測試也能採黑箱；紅隊可深入特定攻擊路徑。BAS 仍需人工設計情境、批准範圍及判讀結果，不能等同完全無人操作或一定算出投資報酬。

**整理者完整作答**：

| 面向 | 滲透測試 | 紅隊演練 | BAS |
|---|---|---|---|
| 主要目的 | 在指定範圍驗證弱點能否被利用及其影響，供修補 | 模擬特定威脅或目標，評估組織預防、偵測、應變能力 | 用可重複測試檢查安全控制對既定攻擊行為是否有效 |
| 範圍 | 應用、主機、網路等限定資產，依授權規則深度測試 | 可橫跨技術、人員與流程，依演練目標及規則執行 | 平台提供或自訂的攻擊情境、測試代理及受控環境 |
| 執行方式 | 自動掃描加人工分析與利用，黑／灰／白箱皆可 | 依威脅情報選擇行為鏈，必要時含社交工程、橫向移動 | 自動或半自動執行既定行為，再彙整阻擋與告警結果 |
| 時間及協作 | 通常有固定窗口，完成後修補與複測 | 依任務持續數日或數週，可採隱蔽演練或與防守方協作 | 可排程頻繁重測，適合規則調整後確認控制是否退步 |
| 產出 | 可重現弱點、利用證據、風險及修補建議 | 攻擊路徑、達成目標情形、偵測與應變缺口 | 各情境的阻擋／偵測率、控制缺口與趨勢 |
| 主要限制 | 受時間、範圍及測試者能力限制，不保證找出所有弱點 | 成本及協調較高，結果依目標與情境，不等於全面弱點清單 | 情境及模擬真實度有限，不能取代人工創造性攻擊或整體流程演練 |

同一機構可先以滲透測試修補網站弱點，再以紅隊檢查從初始入侵到業務目標的防禦鏈，最後以 BAS 定期重測已改善的控制。三者都要明確授權、限制影響、保存證據及安排復測，沒有哪一者必然找出全部問題。

**版本說明**：以上是 114 年已存在的方法與用途；現行產品的自動化深度依平台而異，不用產品行銷功能反推定義。

**官方依據**：[NIST SP 800-115](https://csrc.nist.gov/pubs/sp/800/115/final)；[MITRE 對手模擬計畫](https://attack.mitre.org/resources/adversary-emulation-plans/)；[MITRE 微型模擬計畫](https://ctid.mitre.org/projects/micro-emulation-plans/)。

## 三、路徑遍歷、XSS 與越界讀取（25 分）

**最佳一份**：Aaron Lim，2025-07-11，essay-546845，詳解 6534558，評價 1／0。其五張附圖已放大讀取。此主解主要處理第一小題，第二、三小題由整理者完整補寫。另兩小題可讀文字曾查核，各有一份同作者詳解、評價均 1／0；不把尚未逐圖核對的 XSS 原文列為已全文通過。

**網友摘要及修正**：主解指出操控檔案路徑，離開限定目錄讀取設定、原始碼等檔案，並採間接檔案識別與最小權限。定義合理，但「任意檔案」仍受服務帳號權限限制；現代 Linux 密碼雜湊通常在 shadow，passwd 主要含帳號資料。圖中 `file:` 表示法須視程式是否接受 URI，不能當成通用絕對路徑。單靠移除 `../` 容易被不同解析方式繞過。

**整理者作答，（一）路徑遍歷，5 分**：程式將外部輸入拼成檔案路徑，卻未確認解析後仍位於允許目錄。攻擊者使用上層目錄元素、絕對路徑或不同編碼，令實際開啟的檔案離開限定目錄。以下載功能為例，原本只能取公開文件，卻因未檢查路徑而讀到目錄外的應用設定檔，可洩漏資料庫連線資訊；若存在可寫入功能，還可能覆寫帳號可寫的檔案。效果取決於操作種類、權限及路徑解析。

防禦以不透明檔案 ID 對映伺服器預定路徑，並逐次檢查使用者授權；必要時正規化路徑，驗證其位於允許的目錄邊界，處理符號連結及競態，拒絕不支援的絕對路徑與 URI。服務使用最小權限，機敏檔案不放公開目錄。WAF 可補強監測，不能取代修正。

**整理者作答，（二）XSS，10 分**：網站將攻擊者可控制的資料放入 HTML 或危險 DOM 操作，未依上下文編碼或淨化，瀏覽器因而把資料解讀為腳本並在受害網站的 origin 執行。反射型從請求回傳、儲存型先存入留言等資料再顯示、DOM 型由前端將不可信來源流入危險 sink。三者可能有重疊，不應只按資料是否進資料庫來區分全部情境。

例如留言顯示沒有編碼，含測試腳本的留言被其他使用者開啟後觸發程式，即證明不可信資料可執行。成功利用可能修改頁面、讀取可由腳本存取的敏感內容，或以受害者權限呼叫站內功能。其原理是惡意腳本取得該網站來源的執行環境，不能籠統說成繞過同源政策；HttpOnly Cookie 無法直接被 `document.cookie` 讀取，但仍不能防止腳本代使用者操作。

防禦依 HTML、屬性、URL 等上下文採安全輸出，純文字優先使用一般元素的 `textContent`，避免把輸入交給 `innerHTML`、`eval` 等；必要富文字用維護中的淨化器。CSP、Cookie 屬性及 WAF 是額外防線，不代替根因修正。

**整理者作答，（三）越界讀取，10 分**：程式的索引、指標或讀取長度未經完整檢查，從物件有效邊界之外讀取資料。以長度欄位為例，程式只有 1024 bytes 的有效 buffer，卻信任外部宣稱的 65536 bytes，回傳超過邊界的內容；可能洩漏鄰近記憶體的權杖、密碼或其他資料，也可能造成程序當機及拒絕服務。

若實際配置 65536 bytes，只初始化其中 1024 bytes，再讀取整個配置，單憑這些條件不構成越界讀取；它可能是未初始化資料洩漏。這正是原網友例子必須修正的地方。越界讀取也不等同寫入溢位，不能保證取得程式執行權或解密所有歷史 TLS 通訊。

防禦同時檢查宣稱長度、實收長度及配置容量；驗證非負索引及上界，在運算前防止整數溢位，使用安全語言或具邊界檢查的介面，配合模糊測試及記憶體偵錯。初始化資料可避免部分資料洩漏，但不能替代邊界驗證；stack canary 與 ASLR 也不是所有越界讀取的根本修補。

**考試當時與現行**：三類弱點的原理在 114 年已成立；現行 CWE 頁面例子可能更新，但本題依核心定義作答，不新增當時不存在的事件。

**官方依據**：[MITRE CWE-22](https://cwe.mitre.org/data/definitions/22.html)；[OWASP XSS Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross_Site_Scripting_Prevention_Cheat_Sheet.html)；[MITRE CWE-125](https://cwe.mitre.org/data/definitions/125.html)。

## 四、EDR、防毒及 WAF 的三面向比較（25 分）

**最佳一份**：Aaron Lim，2025-07-11，essay-546848，詳解 6534579，評價 1／0，全文可讀。

**網友摘要**：EDR 著重端點行為與應變，防毒著重惡意程式防護，WAF 著重網站請求防護，可將相關告警整合至 SIEM。

**查核及修正**：現代防毒不只靠靜態病毒碼，也可能有行為、雲端及機器學習偵測，並能主動阻擋；EDR、防毒及 WAF 的 SIEM 整合沒有固定高低等級，取決於日誌內容、介面、連接器、授權及設定。

**整理者完整作答**：

| 面向 | EDR | 防毒軟體 | WAF |
|---|---|---|---|
| 核心功能 | 收集程序、檔案、登錄及網路等端點活動，關聯行為、調查攻擊鏈、獵捕威脅與應變 | 辨識、阻擋、隔離及清除惡意程式，結合特徵、啟發式及其他偵測能力 | 檢查 HTTP／HTTPS 應用請求與規則，防禦 SQL Injection、部分 XSS 等網站攻擊 |
| 主動防禦 | 視產品及設定終止程序、隔離主機、封鎖指標或自動調查；須控制誤判影響 | 即時掃描可在執行或寫入時阻擋、隔離，部分支援行為防護；不應說成只能事後清除 | 在適當攔截位置阻擋惡意請求、限速或要求挑戰，可作虛擬修補；誤判及繞過須持續調整 |
| SIEM 整合 | 傳送告警、調查事件及依能力提供遙測；可透過 API 與應變流程連動 | 傳送偵測、隔離、掃描及更新狀態，供跨端點及其他來源關聯 | 傳送請求、匹配規則、動作、來源及應用欄位，供辨識攻擊活動及後續調查 |

EDR 與防毒可在同一端點產品中並存，但核心用途仍應區分。WAF 必須能取得待檢查的 HTTP 內容；HTTPS 部署涉及適當解密或終止位置，不能假定只看加密封包就能檢查所有應用內容。三者都不能單獨覆蓋全部風險。

整合時統一時間、資產與使用者識別，保留規則、嚴重度及處置結果。例如 WAF 發現網站利用請求，EDR 看到 Web 程序產生異常子程序，再由 SIEM 關聯同一主機與時間，提升調查可信度；自動隔離需符合批准的應變規則，並非收到一則告警即全面封鎖。

**考試當時與現行**：114 年即可用上述三面向作答。現行產品功能會擴展，應以實際部署能力決定整合深度，不把新功能當成所有舊版產品都有。

**官方依據**：[Microsoft Defender 端點功能與 SIEM 整合](https://learn.microsoft.com/en-us/defender-endpoint/microsoft-defender-endpoint-windows)；[Defender 的 SIEM 整合方法](https://learn.microsoft.com/en-us/defender-endpoint/partner-applications)；[NIST SP 800-41 Rev.1](https://nvlpubs.nist.gov/nistpubs/legacy/sp/nistspecialpublication800-41r1.pdf)；[NIST SP 800-92](https://csrc.nist.gov/pubs/sp/800/92/final)。
