# 115 年高考三級資通安全：資通安全防護技術

查核日：2026-10-10。[阿摩試卷 142321](https://yamol.tw/exam/142321)四題與本地原題一致，各有一份詳解、申論作答均 0。網友內容採署名摘要，以下完整答案由整理者補寫。

## 一、API 四面向防護（25 分）

**最佳一份**：Aaron Lim，2026-09-19，essay-582616，詳解 7511305，贊成／反對 1／0。

**網友摘要與查核**：提出 OAuth／PKCE、權杖生命週期、物件授權、限流及輸入輸出限制。方向可採；JWT、非對稱簽章、15 分鐘期限與憑證釘選不是所有 API 的必要條件，UUID 不能代替授權，API 金鑰也不能單獨證明終端使用者身分或防重播。

**整理者完整作答**：

1. **身分驗證與 Token 管理**：全程使用正確驗證憑證的 TLS；行動 App 可採授權碼流程加 PKCE，登入身分需相應鑑別機制，OAuth 本身為授權框架。系統串接以受控服務身分、適當 mTLS 或其他憑證驗證，權限限定至必要資源。權杖短效且限制 scope／audience，安全保存、更新、輪替與撤銷；不得放在 URL 或一般日誌。使用 JWT 時核對允許演算法、簽章、發行者、接收者與時效；簽章不代表內容保密，亦不防止被偷的 bearer token 被使用，必要時採發送者約束與重播防護。
2. **物件層級授權**：每次由伺服器驗證主體對特定物件及操作的權限，納入租戶、擁有／分享關係與角色；預設拒絕，禁止只相信客戶端 ID 或角色。另管制敏感欄位的讀寫與管理功能，測試跨帳號／租戶及不同操作。隨機 ID 只減少猜測，不能修補缺少授權檢查。
3. **流量限制**：按帳號、服務身分、來源、端點及全域容量設定配額、並行數及請求頻率，防分散來源規避；限查詢深度、批次大小、分頁、上傳大小與處理時間。過量可回 429 並提供適當重試提示，監測異常及限制昂貴操作；外部依賴配逾時、受控重試與斷路，避免放大故障。
4. **輸入輸出控管**：依 schema 驗證型別、長度、範圍及允許欄位，避免大量賦值；查詢採參數化，不把資料當 SQL／指令執行。回傳採允許清單及必要最少欄位，敏感內容先確認授權，再考量遮罩；遮罩不能代替授權。錯誤不洩漏堆疊、秘密或內部結構，日誌也需保護。按輸出使用情境編碼；CSP 是瀏覽器頁面防護的一環，不能當成 JSON API 的通用注入防護。

例如 `GET /orders/{id}` 必須檢查目前身分可否讀取該筆訂單，改用 UUID 後仍需同一檢查；匯出端點需另限筆數與權限。

**考試當時與現行**：115 年已可採 OAuth 安全最佳實務與 OWASP API 2023，不把某個產品或權杖格式當唯一解。**標準／原始來源**：[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html)；[OWASP API Security Top 10 2023](https://api-security.owasp.org/editions/2023/en/0x11-t10/)。

## 二、容器化部署風險及四面向防護（25 分）

**最佳一份**：Aaron Lim，2026-09-19，essay-582617，詳解 7511307，0／0。

**網友摘要與查核**：識別共享核心、映像供應鏈、過度權限與横向活動，提出來源驗證、權限限制、網路政策及監控。方向可採；Linux capabilities 不等於系統呼叫清單，seccomp 與 SELinux／AppArmor 的作用不同；非 root 不保證核心被攻陷後仍安全，唯讀根檔案系統亦不能阻止記憶體或可寫掛載攻擊。直接刪除受害 Pod 可能失去證據。

**整理者完整作答**：容器通常以作業系統層級隔離且共用宿主核心，需防核心／runtime 弱點、逃逸、惡意或脆弱映像、秘密外洩、錯誤掛載、編排管理面失陷、橫向移動及資源耗盡。

| 面向 | 防護措施及目的 |
|---|---|
| 映像檔來源 | 只採可驗證來源，保護 registry 推送／拉取權限；掃描套件、惡意內容與嵌入秘密，採精簡且維護中的基底；以不可變摘要識別核准版本，驗證簽署者與來源證明，修補後重新建置及部署。私有倉庫本身不保證內容可信 |
| 權限設定 | 非 root、禁止非必要提權與 privileged、移除不必要 capabilities，避免掛載宿主敏感目錄或管理 socket；限制服務帳號權限、CPU／記憶體等資源，按需要唯讀根檔案系統及分離可寫目錄；以 seccomp 限制系統呼叫，SELinux／AppArmor 限制資源存取；保護外部供給的秘密 |
| 網路隔離 | 依工作負載信任與機敏程度分區，預設拒絕入站／出站並只放行必要依賴，驗證平台與 CNI 確實執行政策；保護管理面，服務間視需要鑑別與加密，控制對外連線及 Web 入口 |
| 執行監控 | 收集容器、宿主、runtime 及編排稽核日誌，關聯程序、檔案、權限與連線異常，保護與集中保存紀錄；按核准劇本隔離，保存必要易失證據及映像／設定，調查影響範圍後由乾淨映像重建，修補共同宿主及其他受影響資產 |

容器隔離不能代替應用授權與安全程式設計，WAF、服務網格、eBPF 是可選實作，不是全部容器部署的法定或技術必要條件。

**考試當時與現行**：採一般容器風險與控制原則；具體產品語法按使用版本查證，本文不把網友示意語法當成可直接部署設定。**官方標準來源**：[NIST SP 800-190](https://csrc.nist.gov/pubs/sp/800/190/final)，第 3、4 節。

## 三、異常登入、MFA 推播及大量下載（25 分）

**最佳一份**：Aaron Lim，2026-09-19，essay-582618，詳解 7511308，0／0。另顯示一則推薦筆記，但不是第二份公開詳解；主解覆盖全部情境。

**網友摘要與查核**：判為密碼噴灑、MFA 疲勞及資料外傳，配合驗證、風險偵測與應變。核心合理；號碼比對不能保證阻止 AitM，也不等同 FIDO 抗釣魚。成功登入未必是合法授權，大量下載還須確認工作需求與證據。一般驗證日誌不應記明文密碼，不能要求用 SIEM 比對使用者實際輸入密碼。

**整理者完整作答**：

1. **不同帳號反覆使用少數密碼**：符合 Password Spraying 特徵，與對單一帳號試大量密碼的暴力猜測不同；若用已洩漏帳密組合則是 Credential Stuffing，不能僅憑題述直接認定後者。
2. **大量 MFA 推播**：可能為 MFA 疲勞／推播轟炸，誘使人誤按同意，可伴隨冒充客服。應拒絕非本人操作的驗證並通報；核對日誌與憑證是否失竊。
3. **登入後大量下載**：可能為受害帳號資料蒐集、外傳或內部濫用，亦須排除合法批次作業；確認資料種類、權限、實際傳輸與範圍，不能只依流量就判定已外洩。

防護採長且不重用的密碼、阻擋已洩漏／常見弱密碼、密碼管理器；按帳號、來源及全域識別分散式嘗試，適當限流與鎖定，避免鎖定本身成為 DoS。採抗釣魚 FIDO2／WebAuthn 等適當驗證，號碼比對可減輕單純推播疲勞但仍需教育與防釣魚；停用不必要的舊式驗證與復原繞過管道。保護 session，風險升高時重新驗證並限制權限。

資料存取落實最小權限、物件授權、批次下載額度與敏感操作核准，監控及必要 DLP。事件時保存登入、MFA、session 與資料存取紀錄，撤銷可疑工作階段／權杖，調查與限制受害帳號，依授權安全重設憑證、復原與通報；關聯異常時間、主體、來源與失敗模式，不收集明文密碼。

**考試當時與現行**：攻擊特徵與控制相同，抗釣魚能力須看協定及整體登入／復原流程。**官方來源**：[CISA 身分存取管理最佳實務](https://www.cisa.gov/sites/default/files/2023-12/ESF%20IDENTITY%20AND%20ACCESS%20MANAGEMENT%20RECOMMENDED%20BEST%20PRACTICES%20FOR%20ADMINISTRATORS%20PP-23-0248_508C.pdf)；[CISA MFA 指引](https://www.cisa.gov/audiences/small-and-medium-businesses/secure-your-business/require-multifactor-authentication)。

## 四、軟體供應鏈攻擊與五面向防護（25 分）

**最佳一份**：Aaron Lim，2026-09-19，essay-582619，詳解 7511304，0／0。

**網友摘要與查核**：由上游元件、建置或發布鏈植入惡意軟體，主張安全開發、相依管理、管線保護、驗簽與 SBOM。方向合理；封閉或乾淨建置不自動保證可重現，簽章不能證明程式沒有惡意邏輯，SBOM 不能保證數分鐘完成所有衝擊分析，也不是漏洞掃描工具。

**整理者完整作答**：軟體供應鏈攻擊利用開發、相依元件、建置、簽署、發布或更新途徑的信任與弱點，污染下游使用的軟體或構件。可能涉及套件投毒、名稱仿冒、相依性混淆、管線或簽署金鑰失陷與更新置換，並不限於一定攻擊第三方或一定大規模散播。

1. **安全開發流程**：訂安全與供應商需求、威脅分析、審查和測試；保護版本庫、分支及變更核准，掃描秘密與程式弱點，追蹤修補及交付例外。開發者本機 hooks 可被繞過，重要檢查應在受控管線強制執行。
2. **第三方套件管理**：盤點直接／遞迴相依，確認來源與維護狀況；採受控代理與正確命名解析，鎖定核准版本及驗證摘要，持續比對漏洞與惡意套件風險，訂更新、汰換及例外期限。摘要釘選也可能固定住原本就惡意的套件，仍需審查來源。
3. **CI/CD 管線保護**：最小權限、MFA、短效受限憑證、秘密管理；分離不可信 PR 與可存取簽署／部署秘密的工作，保護管線設定與 runner，採乾淨隔離建置及受控依賴，限制連網，保留稽核與產出關聯。可重現性須額外控制全部輸入與非決定性因素。
4. **軟體簽章與來源驗證**：保護簽署金鑰與批准流程，簽署核准構件；部署前驗證簽署者、信任鏈、有效性、摘要、來源證明與政策，處理撤銷／輪替。來源證明描述從何種來源與建置產出，驗簽證明指定內容由受信任身分簽署且未被更動，不代表必然安全。
5. **SBOM**：產生與特定版本／構件綁定的機器可讀元件清冊，保存名稱、版本、識別及相依關係等資訊，保護完整性並更新；用於定位受影響元件、供應商追蹤與弱點處置。可配合具依據且持續更新的 VEX 說明受影響狀態，仍需確認實際部署、可達性、補償措施及修補。

**考試當時與現行**：115 年作答可依 SSDF 及當時 SBOM 指引；CISA 另於 2026-07-29 發布更新的最小元素指引，實務交付應依契約與適用版本查核，不能因更新便認定所有組織立即受其法律強制。

**官方標準／來源**：[NIST SSDF SP 800-218](https://csrc.nist.gov/pubs/sp/800/218/final)，PO、PS、PW、RV；[CISA SBOM 資源](https://www.cisa.gov/topics/cyber-threats-and-advisories/sbom/sbomresourceslibrary)；[CISA 2026 更新公告](https://content.govdelivery.com/accounts/USDHSCISA/bulletins/422a7eb)。
