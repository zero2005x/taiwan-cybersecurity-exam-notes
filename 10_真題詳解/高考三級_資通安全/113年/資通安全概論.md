# 113年高考三級資通安全：資通安全概論

查核日期：2026-10-10。阿摩試卷：[121214](https://yamol.tw/exam/121214)。四題題文與本地轉錄核對一致。以下網友內容為整理者以自己的語句歸納的署名摘要；完整作答為整理者核對與補寫，不是官方標準答案。

## 第1題：社交工程

**題目**：請說明何謂社交工程攻擊，並詳述常見的社交工程攻擊方式及相對應防護措施。（25分）

**採用詳解**：nomi，2024/11/11，詳解#6247625；全部詳解1則，讚10、倒讚0。

**網友摘要**：攻擊者利用人性及信任，假冒人員、寄送釣魚郵件、提供假軟體或即時通訊連結，騙取機敏資訊或植入惡意程式。

**先行檢查**：定義與主要手法合理；MSN例子已過時，原文防護大多停留在提高警覺，且「就能避免」過於絕對。採為唯一主解，以下補足題目要求的逐項防護。

**整理者完整作答**：社交工程透過心理操控、冒用身分及誤導流程，使人員交出資訊、提供存取權或執行危險操作，不必先突破技術漏洞。

| 手法與例子 | 對應防護 |
|---|---|
| 郵件／簡訊釣魚：以帳號即將停用誘導進入假登入頁 | 從已知官方入口登入；核對網域；部署郵件過濾並提供通報管道 |
| 電話假冒IT或主管：要求提供密碼、OTP或核准MFA | 依既有名冊獨立回撥核實；不得交付驗證祕密；採抗釣魚MFA |
| 商務郵件詐騙：冒用主管要求變更匯款資料 | 付款及受款資料變更採雙人核准、獨立管道確認 |
| 假更新／誘餌下載：以工具或USB誘使執行惡意程式 | 從可信管道部署軟體；限制外接媒體與程式執行；使用端點偵測 |
| 尾隨進入機房或假冒維護廠商 | 驗證訪客身分、陪同及登記；門禁防尾隨；紙本機敏資料妥善銷毀 |

組織另應施行最小權限、分工核准、持續演練及不責備的通報文化；發現異常即停下操作、通知窗口，依事件程序隔離與調查。單一教育或技術工具均不能保證零風險。

**當年與現行**：基本攻擊原理相同。現行補充AI仿聲／深偽冒充及MFA疲勞攻擊；獨立核實及抗釣魚驗證更重要，不能只憑聲音、頭像或熟悉文風信任對方。

依據：[CISA釣魚辨識指引](https://www.cisa.gov/secure-our-world)、[CISA安全宣導資源](https://www.cisa.gov/resources-tools/resources/secure-our-world-cybersecurity-awareness-month-resources)。前者目前標示封存，作為一般防護原則參考，不當作現行法律義務。

## 第2題：數位簽章與CA憑證

**題目**：說明數位簽章的學理特性，及實務上使用可信賴CA依法簽發憑證的原因。（25分）

**採用詳解**：nomi，2024/11/11，詳解#6247634；全部詳解1則，讚6、倒讚0。

**網友摘要**：簽章支援完整性、簽署人鑑別及不可否認性；憑證讓接收者取得可用於驗證的公鑰，並支援實務法律效力。

**先行檢查**：三項性質正確。但以「私鑰加密雜湊」概括所有演算法不精確；ECDSA、EdDSA並非這種加密／解密程序。私鑰也可能遭竊，不能說持有人以外絕不可能持有。原解將數學簽章成立與法定推定效力混在一起，以下修正後採用。

**整理者完整作答**：簽署端以訊息及私鑰執行簽章演算法，驗證端以訊息、簽章及對應公鑰執行驗證。

1. 完整性：訊息遭變更時，原簽章通常無法通過驗證。
2. 來源鑑別：確認簽章由對應私鑰產生；真實身分還須靠可信公鑰綁定。
3. 不可否認性：簽章可作為簽署事實的證據，但須考慮私鑰保管、外洩、憑證有效性、時間及證據保存。
4. 不提供訊息機密性：內容保密需另外加密。

CA在核驗申請者後簽發憑證，把身分與公鑰綁定，並以CA簽章支持信任鏈。驗證者應檢查憑證鏈、用途、有效期間、撤銷狀態及演算法強度；長期文件還可能需要可信時間戳與保存當時的驗證資訊。這能降低公鑰被替換的冒充風險。

**當年法規**：113年5月15日修正公布的《電子簽章法》適用於113年高考期間。第2條定義法律上的數位簽章；第6條對符合主管機關許可之憑證機構、有效且未逾使用範圍的憑證所作數位簽章，提供本人簽名或蓋章的推定。第12條要求憑證實務作業基準經許可後始得提供簽發憑證服務。一般數學簽章能驗證，不因此自動滿足該項法律推定條件。

**現行補充**：另核對施行細則對CA註冊身分識別與認證程序的要求。仍須區分「技術驗證成功」「法律推定」及個別業務法令的適用限制，不能保證任何簽章都永遠不可爭執。

依據：[NIST FIPS 186-5](https://csrc.nist.gov/pubs/fips/186-5/final)、[電子簽章法](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=J0080037)、[電子簽章法施行細則](https://law.moj.gov.tw/LawClass/LawAll.aspx?pcode=J0080039)。

## 第3題：SQL注入

**題目**：說明SQL注入的可能原因，並詳述系統改善方案。（25分）

**採用詳解**：nomi，2024/11/11，詳解#6247686；全部詳解1則，讚7、倒讚0。

**網友摘要**：提出參數化查詢、輸入檢核、限制資料庫權限及程式弱點掃描。

**先行檢查**：方向符合OWASP，但「在N-Tier架構下如何預防」只是問題句，未提供措施；缺少核心成因及防禦主次。以下補足。

**整理者完整作答**：SQL注入的根本原因是應用程式把不可信輸入拼接進SQL，讓原應屬資料的輸入變成查詢語法。動態SQL、錯誤使用ORM、儲存程序內再次拼接字串都可能形成漏洞。資料庫權限過大或錯誤訊息外露則放大危害。

例如將帳號直接串入 `WHERE username='輸入值'`，攻擊者可能改變條件，造成繞過驗證或資料外洩。

1. 首要措施是參數化查詢：先固定SQL結構，再繫結資料，如 `SELECT ... WHERE username = ?`。資料值不被解析成SQL指令。
2. 表名、欄位名、排序方向通常不能用資料參數取代；應映射至程式內固定允許清單。
3. 驗證型別、長度、範圍與格式；這是輔助措施，不能取代參數化。
4. 資料庫帳號採最小權限，讀寫分工，避免DBA權限；隔離資料庫網路及管理介面。
5. 對外回傳一般錯誤，詳細資訊放在受保護日誌；偵測異常查詢。
6. 以程式碼審查、SAST及DAST驗證修正；安全儲存程序亦不得內含不安全動態SQL。WAF作輔助緩解，不替代程式修補。

**當年與現行**：防禦核心均為程式碼與資料分離。不可把全面字元跳脫、黑名單或使用ORM本身當成充分防禦。

依據：[OWASP SQL Injection Prevention](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)。

## 第4題：去識別化

**題目**：詳述至少兩種常用於防止洩露個人隱私或機敏資料的去識別化方法。（25分）

**採用詳解**：nomi，2024/11/11，詳解#6247688；全部詳解1則，讚5、倒讚0。頁面已可讀取。

**網友摘要**：移除直接識別資料，並對生日、郵遞區號等準識別資訊採泛化或抑制。

**先行檢查**：這兩類方法正確，但需要交代重識別風險與資料效用取捨。只刪姓名不能保證匿名。

**整理者完整作答**：去識別化是降低資料與特定個人連結能力的處理程序，應先辨識直接識別欄位與可透過外部資料交叉連結的準識別欄位。

1. **移除／抑制**：刪除姓名、身分證字號、聯絡資訊；對罕見組合或高風險紀錄抑制部分欄位或整筆資料。優點是容易實作，代價是損失細節；其他欄位仍可能辨識個人。
2. **泛化**：把精確年齡改成區間、完整地址改成較大地理區域、日期改成年或月，使多筆紀錄共享相同準識別特徵。可用k匿名衡量某些重識別風險，但仍可能發生屬性推論或背景知識攻擊。
3. **假名化作補充**：以代碼取代身分，對照表分離保存並限制存取。可支持資料連結，但若能用對照表還原，仍不能直接宣稱完全匿名。

實務應評估資料發布目的、接收者與外部可取得資料，測試重識別風險，審查小樣本與罕見組合，並配合存取限制及禁止重識別條款。公開統計可評估差分隱私；擾動機制與參數需明確設計，不能任意加噪即宣稱保證隱私。

**當年與現行**：NIST SP 800-188於2023年公布，113年已可參考。基本方法未變；現行使用仍需評估外部資料增加後的連結風險，不能把「去識別化」直接等同永久不可還原。

依據：[NIST SP 800-188](https://csrc.nist.gov/pubs/sp/800/188/final)。
