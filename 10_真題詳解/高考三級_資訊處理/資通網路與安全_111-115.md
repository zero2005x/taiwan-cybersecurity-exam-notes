**題目**（阿摩題文）：(一)TCP（Transmission Control Protocol）和 UDP（User Datagram Protocol）都位於傳輸層，請說明這兩個協定各自有何特色？（10 分）
(二)請詳細說明何謂 TCP 三方握手（3-way handshaking）協定？（5 分）

**網友主解摘要與查核**：本題拆三頁。（一）蟲不易版（有幫助 11）比較連線、流量與壅塞控制及適用服務，正確精簡，選為主解；Aaron Lim 表格版（有幫助 10）可對照。（二）瑩版（有幫助 10）列 SYN、SYN-ACK、ACK 並附連線結束的四次揮手，正確，選為主解；Jane Yen 版內容是 TCP／UDP 比較，答非所問。（三）Jane Yen 版（有幫助 10）說明半開連線、SYN Flood 與 SYN Cookie 等防護，選為主解，但其列入的 RST 攻擊與三方握手無關，作答時不宜列入；蟲不易版正確但簡略。以下補寫完整作答。

**整理者作答**：

**（一）TCP 與 UDP 的特色（10 分）**

| 項目 | TCP | UDP |
|---|---|---|
| 連線 | 連線導向，傳資料前先以三方握手建立連線，結束以四次揮手釋放 | 非連線導向，直接送出資料報 |
| 可靠性 | 序號、確認（ACK）、逾時重傳，保證不遺失、不重複、依序送達 | 不保證送達與順序，遺失不重傳（只有選用的檢查和） |
| 流量與壅塞控制 | 滑動視窗流量控制、壅塞控制（慢啟動、壅塞避免） | 無 |
| 標頭與效率 | 20 位元組以上，額外負擔較大、延遲較高 | 8 位元組，簡單快速 |
| 傳輸單位 | 位元組串流 | 獨立資料報，保留訊息邊界，可廣播與多播 |
| 典型應用 | HTTP／HTTPS、SMTP、SSH、FTP | DNS 查詢、DHCP、VoIP、視訊串流、線上遊戲、QUIC 底層 |

**（二）TCP 三方握手（5 分）**：（1）用戶端送出 SYN，帶初始序號 x；（2）伺服器回 SYN＋ACK，帶自己的初始序號 y 與確認號 x＋1，並為此連線配置資源，進入 SYN-RECEIVED（半開）狀態；（3）用戶端回 ACK，確認號 y＋1，雙方進入 ESTABLISHED，開始傳資料。目的在同步雙方序號並確認雙向皆可收發。

**（三）三方握手為何會被用於阻斷服務（5 分）**：伺服器在收到 SYN 時就配置資源並放入半開連線佇列，等待最後的 ACK。攻擊者大量送出偽造來源 IP 的 SYN（SYN Flood），伺服器回的 SYN＋ACK 送到不存在或不回應的主機，半開連線要等到逾時才釋放，佇列很快被占滿，合法用戶的連線請求就被拒絕。防護：SYN Cookie（收到 ACK 前不配置狀態）、縮短半開逾時、加大佇列、防火牆或負載平衡器代理握手（SYN Proxy）、速率限制與上游流量清洗。

**題目**（阿摩題文）：(一)NAT 的功用及原理為何？又使用 NAT 有何缺點？請說明之。（15 分）
(二)許多公司使用 NAT 的目的是降低網路遭受攻擊的風險，請說明其理由。（5 分）

**網友主解摘要與查核**：（一）Zong Huang 版（有幫助 10）說明 NAT 功用、原理與效能、相容性、追蹤三項缺點，正確，選為主解；瑩的筆記以圖說明概念，一起撐住一起上榜版較簡略。（二）wan han 版與 Zong Huang 版各有幫助 10；Zong Huang 版列隱藏內部 IP、減少攻擊面等，較完整，選為主解，但「NAT 可防止埠掃描」須靠防火牆規則，NAT 本身不是安全機制，以下補正。

**整理者作答**：

**（一）功用、原理與缺點（15 分）**
- **功用**：讓使用私有 IP（RFC 1918，如 10.0.0.0/8、192.168.0.0/16）的內部主機共用少數公有 IP 上網，節省 IPv4 位址；也可隱藏內部定址、方便更換 ISP。
- **原理**：NAT 設備（路由器或防火牆）改寫經過封包的位址並記錄對應表。靜態 NAT 一對一對應；動態 NAT 從位址池分配；最常見的 PAT／NAPT 以「公有 IP＋不同來源埠」區分多台內部主機：內部主機 192.168.1.10:51000 外送時被改成 203.0.113.5:40001 並記入轉換表，回應封包依表改回原位址與埠送回內部。
- **缺點**：破壞端對端連通，外部無法主動連入內部主機，需另設埠轉送；部分協定（FTP 主動模式、SIP、IPsec AH）在封包內容嵌入位址或保護標頭，需 ALG 或 NAT-T 才能運作；改寫封包增加處理負擔與延遲；多人共用 IP 使日誌追查與 IP 封鎖困難；P2P 與即時通訊需打洞技術。

**（二）為何能降低遭攻擊風險（5 分）**：內部主機使用私有 IP，外部看不到真實位址與網路架構；PAT 只有內部主動發起、轉換表中已有對應的連線回應才會被轉送進來，外部主動掃描或連線找不到對應而被丟棄，效果類似狀態檢測的「預設拒絕入站」。但 NAT 不是安全機制：無法防止使用者主動連到惡意網站、釣魚或內部橫向攻擊，埠轉送出去的服務仍直接暴露，仍須搭配防火牆政策。

**整理者作答**：

**（一）功能與部署位置的區別（15 分）**

| 項目 | 防火牆 | 入侵偵測系統（IDS） |
|---|---|---|
| 功能 | 依政策（IP、埠、協定、連線狀態、應用）允許或拒絕流量，屬「存取控制、預防」 | 監看流量或主機活動，以特徵比對與異常分析找出攻擊並告警，屬「偵測」，本身不阻擋 |
| 對已允許流量 | 不檢查內容（傳統防火牆） | 檢查內容，可發現走合法埠的攻擊 |
| 部署 | 串接（inline）在網路邊界、內外網與 DMZ 之間，所有流量必經 | 多以旁路方式，經交換器鏡像埠（SPAN）或分流器（TAP）接收副本，部署在防火牆內側、DMZ、核心網段；主機型則裝在伺服器上 |
| 失效影響 | 故障會中斷連線 | 故障不影響連線，但失去偵測 |
| 輸出 | 放行／丟棄與日誌 | 告警，交由人員或 SIEM 處理 |

**（二）主機型與網路型 IDS 的差別（5 分）**：主機型（HIDS）安裝在個別主機，分析系統日誌、檔案完整性、登錄檔、行程與系統呼叫，可看到加密解開後的行為與本機攻擊，但需逐台安裝、耗主機資源、主機被攻陷時可能被關閉。網路型（NIDS）部署在網段上分析封包，可一次監看多台主機、對主機透明，但看不到加密內容與主機內部行為，在高流量下可能漏封包。

(二)請說明完整性，並說明其主要演算法暨應注意事項。

**網友主解摘要與查核**：（一）陳小刀版（有幫助 10）說明機密性並列公鑰加密、數位簽章、金鑰交換，選為主解，但數位簽章提供的是完整性與來源鑑別，不是機密性，作答時應區分。（二）陳小刀版（有幫助 10）列數位簽章與訊息摘要並舉 MD5、SHA-1，選為主解，但 MD5、SHA-1 已不安全，且單純雜湊無法防範同時竄改資料與摘要，須用 HMAC 或簽章，以下補正。另有申論作答 2 份（付費未解鎖）。

**整理者作答**：

**（一）機密性及以非對稱式密碼學達成（15 分）**：機密性是確保資訊只讓經授權的人或程序取得與揭露。非對稱式密碼學使用公鑰與私鑰一對：任何人可用接收者的公鑰加密，只有持有對應私鑰的接收者能解密，不必事先共享秘密。實務作法：（1）直接加密：以 RSA-OAEP 加密少量資料；（2）混合加密（主流）：隨機產生對稱工作階段金鑰，以 AES 加密大量資料，再以接收者公鑰加密（封裝）該對稱金鑰，例如 S/MIME、PGP；（3）金鑰協議：TLS 1.3 以（EC）DHE 讓雙方在公開通道算出共享金鑰，再以 AES-GCM 加密，並具前向保密。應注意：公鑰須經憑證（PKI）確認屬於正確對象，以防中間人攻擊；私鑰妥善保管（HSM、存取控制）；使用足夠長度（RSA 3072 以上、ECC P-256 以上）並規劃後量子密碼遷移（ML-KEM）。

**（二）完整性、主要演算法與注意事項（15 分）**：完整性是確保資訊在儲存與傳輸中未遭未授權的修改、刪除或插入，且可偵測變更。主要演算法：（1）雜湊函數 SHA-256／SHA-384、SHA-3，產生訊息摘要比對；（2）訊息鑑別碼 HMAC、CMAC，以共享金鑰保護摘要，同時確認來源；（3）數位簽章 RSA-PSS、ECDSA、EdDSA，以私鑰簽章摘要，提供完整性、來源鑑別與不可否認性；（4）認證加密 AES-GCM、ChaCha20-Poly1305，加密同時提供完整性。注意事項：不得再用 MD5、SHA-1（已有碰撞攻擊）；單純雜湊無金鑰，攻擊者可同時改資料與摘要，傳輸時須用 HMAC 或簽章；HMAC 比對應使用固定時間比較以防時序攻擊；金鑰與簽章私鑰須妥善管理；驗章需確認憑證有效且未撤銷；搭配防重送（序號、時間戳）。

## 114 年 二、NAT 下服務外部化的限制與解決方法（25 分）

**阿摩查核**：

- [申論頁 547501](https://yamol.tw/exam/128433?info=essay.547501)：Aaron Lim，2025-07-11，詳解 6534695，標示由 GoogleAI 產生，付費，已解鎖查核，有幫助 11／沒幫助 0；Yuchang Wu，2026-01-02，詳解 7270730，付費，已解鎖查核，有幫助 10／沒幫助 0

**題目**（阿摩題文）：二、企業常透過網路位址轉譯（Network Address Translation, NAT）技術來節省公有 IP 位址，然而在進行內部服務外部化（例如公開 Web、Mail、 VPN 等伺服器）時，NAT 設計可能帶來一些限制或挑戰，請說明兩項限制或挑戰並提出對應的兩種解決方法。（25 分）

**網友主解摘要與查核**：Aaron Lim 版（有幫助 11）詳述方向性限制等；Yuchang Wu 版（有幫助 10）列外部無法起始連線與埠轉發、安全與規則複雜度與反向隧道，選為主解，但「以 ngrok 等外部中繼建立反向隧道」會繞過企業邊界管控，不宜作為企業對外服務的正式解法，應改以 DMZ＋靜態 NAT、反向代理或負載平衡器為主。

**整理者作答**：

**限制或挑戰（任兩項詳述）**：
1. **外部無法主動連入**：內部伺服器使用私有 IP，外部使用者只能看到 NAT 的公有 IP，NAT 預設丟棄外部主動發起的連線，Web、Mail、VPN 服務無法被存取。
2. **公有 IP 與埠衝突**：多台伺服器共用一個公有 IP 時，同一埠（如 443）只能轉送給一台主機，多個 HTTPS 服務需改用非標準埠或其他手段。
3. **協定相容性**：FTP 主動模式、SIP、IPsec 等在內容中帶位址或保護標頭，NAT 改寫後失效；VPN 需 NAT-T。
4. **內部存取同一服務（Hairpin NAT）與 DNS 不一致**：內部使用者以公有網域名稱連線，可能因無迴流設定而失敗。
5. **來源 IP 遺失與記錄困難**：經代理或 NAT 後伺服器看不到真實用戶端位址，影響稽核與封鎖。

**解決方法**：
1. **靜態 NAT 或埠轉送（DNAT）**：將公有 IP 的特定埠對應到 DMZ 中的伺服器（如 203.0.113.5:443 → 10.0.10.20:443），並以防火牆只開放必要埠，伺服器放在 DMZ 與內網隔離。
2. **反向代理或負載平衡器**：以一個公有 IP 接收所有 HTTPS，依網域名稱（SNI／Host 標頭）分送到不同內部伺服器，並可同時提供 TLS 終結與 WAF；保留來源 IP 可用 X-Forwarded-For 或 PROXY protocol。
3. 其他：申請多個公有 IP 做一對一靜態 NAT；啟用 ALG 與 IPsec NAT-T；設定 Hairpin NAT 或內外部分離的 Split DNS；長期導入 IPv6 端對端定址（仍需防火牆控管）。

**題目**（阿摩題文）：(一)請解釋何謂「匿名化」（Anonymization）。
(二)請解釋何謂「擬匿名化」（Pseudonymization）。
(三)請舉一個例子說明「匿名化」及「擬匿名化」兩者之差異。

**網友主解摘要與查核**：三個子題頁只有 Aaron Lim 版（ChatGPT 產生，有幫助 3），匿名化、擬匿名化定義與病歷例子正確，選為主解。

**整理者作答**：

**（一）匿名化（10 分）**：以刪除、泛化、遮蔽、加入雜訊、資料彙總等技術，使資料無法以任何合理可能的方式直接或間接識別特定個人，且過程不可逆、沒有可回推的對照資料。依 GDPR 前言第 26 點，真正匿名化的資料不再屬於個人資料，不受 GDPR 規範；我國個資法第 6 條、第 16 條、第 19 條以「無從識別特定當事人」為利用條件之一。須評估再識別風險（如以 k-匿名、l-多樣性檢驗），避免與其他資料比對後重新識別。

**（二）擬匿名化（10 分）**：GDPR 第 4 條第 5 款定義為，處理個人資料使其在不使用額外資訊的情況下無法再歸屬於特定當事人，且該額外資訊（如對照表、金鑰）須分開保存並以技術與組織措施保護。常用方法為以代碼、雜湊（加鹽或 HMAC）或加密值取代姓名、身分證字號等直接識別子。擬匿名化資料仍屬個人資料，持有對照資訊者可還原，仍須遵守個資保護規範，但可降低外洩風險，且是 GDPR 鼓勵的安全措施。

**（三）舉例說明差異（10 分）**：醫院研究資料包含姓名、身分證字號、出生日期、地址與診斷。
- 擬匿名化：把姓名與身分證字號換成研究代碼 P0001，對照表由醫院資訊室另行加密保管，研究人員分析時看不到身分，但日後需追蹤病人或通知檢查異常時，經授權可透過對照表還原，屬可逆。
- 匿名化：刪除姓名、身分證字號與對照表，出生日期泛化為年齡區間、地址泛化為縣市，罕見組合予以抑制，只保留統計所需欄位，任何人（含醫院）都無法再對應到個人，屬不可逆，可作為開放資料。

**整理者作答**：依 ISO 31000／ISO 22301 的風險評估精神，可分為五步：
1. **建立全景與範圍（識別關鍵業務與資產）**：確認 BCM 範圍、關鍵業務功能及其依賴的人員、資訊系統、設施、供應商，並界定風險準則。
2. **風險辨識**：找出可能造成中斷的威脅與弱點，例如勒索軟體、機房斷電、天災、關鍵人員流失、供應鏈中斷。
3. **風險分析**：評估各威脅發生可能性與對業務的衝擊（財務、法遵、商譽、服務中斷時間），結合業務衝擊分析的 RTO、RPO，得出風險值。
4. **風險評量**：將風險值與可接受準則比較並排序，決定需優先處理的風險。
5. **風險處理與監控**：選擇降低、移轉、避免或接受的策略，擬定控制措施並納入營運持續策略與計畫；指定負責人，定期監督、審查並在環境變動後重新評估。

**整理者作答**：

**（一）為何不需直接攻擊內部系統，與自行下載惡意程式的差異（15 分）**：這是軟體供應鏈攻擊。攻擊者入侵供應商的開發、建置或更新伺服器（或竊取其簽章金鑰、劫持更新通道），把惡意程式植入合法更新包或派送任務；客戶端的遠端管理工具本來就具有高權限、受信任並被允許派送程式，因此惡意程式隨「正常更新」自動安裝到大量主機，例如 SolarWinds Orion、Kaseya VSA 事件。可能涉及的方法：入侵供應商建置環境植入後門、竊取或濫用程式碼簽章憑證、入侵供應商的雲端管理平台、竊取遠端管理工具帳密直接派送、相依套件投毒。與使用者自行下載的差異：不需要使用者任何操作；經由受信任通道與合法簽章，安全工具與白名單會放行，日誌也顯示為合法更新；一次感染大量客戶與主機；以高權限執行，影響範圍大；責任與根因位於第三方，較難發現。

**（二）只檢查點擊與未修補弱點為何找不到原因，以及降低風險的三個面向（15 分）**：此攻擊不經郵件也不需利用主機弱點，主機修補完整、員工也未點擊，檢查結果全部正常，真正入口是受信任的第三方工具與更新流程，屬於「信任關係被濫用」。
- **第三方風險管理**：選商時評估供應商資安能力（ISO 27001、安全開發 SSDLC、事件通報義務），契約明訂資安要求、稽核權與通報時限；要求提供 SBOM 與弱點揭露；限制供應商遠端存取（MFA、時段、跳板機、最小權限）並定期複審。
- **更新驗證**：驗證程式碼簽章與雜湊，不只信任來源通道；先在測試區或分批派送（canary）並觀察行為，再全面部署；限制遠端管理工具只能執行經核准的套件，派送需變更管理與雙人核准；關注供應商安全公告。
- **內部監控**：以 EDR 監控管理工具產生的子行程與異常行為；建立正常連線基準，偵測主機異常對外連線與橫向移動；集中記錄遠端管理工具的派送紀錄並與變更單比對；網路分段限制管理工具的影響範圍；發生事件時能快速停用該工具並隔離主機。
