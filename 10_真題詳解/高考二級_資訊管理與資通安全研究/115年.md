## 一、AI Agent 與 OWASP LLM 風險（每小題 10 分，共 30 分）

**題組敘述**：機關 AI Agent 可讀取上傳文件、搜尋內部案件、產製公文草稿並透過 Email API 寄送；外部 PDF 夾帶隱藏指令，要求忽略原指示、查詢其他案件並寄至外部 Email。範圍為 OWASP LLM01、LLM02、LLM06（OWASP Top 10 for LLM Applications 2025 版編號）。

### （一）改變任務並查詢其他案件：LLM01

**阿摩查核**：

- [申論頁 594588](https://yamol.tw/exam/145847?info=essay.594588)：MoAI - 您的AI助手，2026-10-07，詳解 7552839，標示由 MiniMax-M3 產生，付費，已解鎖查核，有幫助 1／沒幫助 0

**題目**：(一) AI 依 PDF 中的隱藏指令，改變原本的處理任務，進一步查詢其他案件資料。判斷主要涉及 LLM01、02、06 那一項，並說明理由？然後提出一項適當的防護改善措施。

**網友主解摘要與查核**：MoAI 判斷為 LLM01 間接提示注入，並說明與 LLM02、LLM06 的區辨與防護，正確，選為主解。

**整理者補寫**：

- **判斷**：主要涉及 **LLM01 Prompt Injection（間接提示注入）**。
- **理由**：惡意指令不是來自承辦人，而是藏在外部 PDF 這種不可信資料中；模型無法區分「資料」與「指令」，被內容劫持而偏離「摘要並產製草稿」的原任務，改去查詢其他案件。問題核心是外部內容改變了模型行為，後續的資料外洩（LLM02）與擅自寄信（LLM06）都由此觸發。
- **防護改善措施（擇一詳述）**：把外部文件標示並隔離為「不可信資料」，以結構化提示把系統指令與文件內容分開（例如以分隔標記包住文件、明示文件內任何指令都不得執行），並在送入模型前以內容過濾或分類器偵測隱藏文字、零寬字元、白字、後設資料中的指令；再搭配限制工具：摘要任務只開放「讀取本文件」能力，不開放案件搜尋。

**題目**：(二) AI 將查詢取得的其他案件資料呈現在回應內容，造成資料洩漏。判斷主要涉及 LLM01、02、06 那一項，並說明有什麼風險？然後提出一項適當的防護改善措施。

**網友主解摘要與查核**：MoAI 判斷為 LLM02，風險與防護說明大致正確，選為主解；但其稱「機關最高可處新臺幣 2 億元罰鍰」有誤，《個人資料保護法》罰鍰規定針對非公務機關，公務機關違法主要是國家賠償、行政與刑事責任，此句不採。

**整理者補寫**：

- **判斷**：主要涉及 **LLM02 Sensitive Information Disclosure**；結果是其他案件的個資與機敏資料被揭露給無權知悉者。
- **風險**：違反個資法目的拘束與最小必要原則（第 5、16 條），侵害當事人隱私，機關負損害賠償與國家賠償責任，承辦人可能涉公務員洩密；案件內容可能涉偵查或公務機密；民眾對 AI 服務失去信任；外洩內容可被進一步利用於社交工程或詐騙。
- **防護改善措施（擇一詳述）**：檢索層落實**以使用者權限為準的存取控制**——AI 呼叫案件查詢時代入承辦人的身分與案件承辦關係（文件層級 ACL），只回傳承辦人原本就有權看的資料，而不是用高權限服務帳號查全部；再於輸出端以 DLP／個資偵測遮罩身分證字號等欄位，並記錄查詢日誌供稽核。

**題目**：(三) AI 未經承辦人確認，即自行呼叫 Email API，將資料寄送至外部指定 Email。判斷主要涉及 LLM01、02、06 那一項，並說明有什麼風險？然後提出一項適當的防護改善措施。

**網友主解摘要與查核**：MoAI 判斷為 LLM06 過度代理，提出人類確認、最小工具權限、收件者白名單等，正確，選為主解。

**整理者補寫**：

- **判斷**：主要涉及 **LLM06 Excessive Agency**。AI 被賦予過多功能（寄信）、過大權限（可寄任意外部位址）與過高自主性（無須人確認即執行有外部影響的動作）。
- **風險**：資料一經寄出無法收回，形成「提示注入→越權查詢→外傳」完整外洩鏈；AI 可被當作對外發送釣魚或垃圾郵件的工具；違反分層負責與公文用印、發文程序；事後難以釐清授權與責任。
- **防護改善措施（擇一詳述）**：高風險動作**人機協同（human-in-the-loop）**：寄信前顯示收件者、附件與內容摘要，須承辦人明確核准；Email API 只允許寄給機關網域或預先核定的收件者白名單、限制附件類型與數量；工具權限依任務最小化，摘要任務不載入寄信工具；所有工具呼叫留存日誌並設異常告警。

## 二、雲端搬遷時廠商說法與資通系統防護基準驗收（30 分）

**阿摩查核**：

- [申論頁 594591](https://yamol.tw/exam/145847?info=essay.594591)：MoAI - 您的AI助手，2026-10-07，詳解 7552797，標示由 MiniMax-M3 產生，付費，已解鎖查核，有幫助 0／沒幫助 0

**題目**：二、某機關自有機房建置的一般性業務網站，現在因設備汰換及維運考量，規劃將網站搬遷至廠商提供的雲端機房，由廠商負責主機、網路及系統維運。廠商提出以下說明：
⑴搬到雲端機房後，管理者的連線管理採 HTTPS 及帳號密碼驗證，因此不需要另外要求遠端存取由機關指定的控制點。
⑵雲端環境本身具有備份及備援機制，發生故障時由廠商負責處理，因此機關不需要另外訂定網站的最大可容忍中斷時間。
⑶系統搬遷後，其使用的作業系統、函式庫、開源套件及雲端服務均由廠商管理，且多是常見元件，因此機關不需要另外掌握完整第三方元件清單。
機關資安人員認為違背下列資通系統防護基準要求：
■ 遠端存取之來源應為機關已預先定義及管理之存取控制點。
■ 訂定資通系統從中斷後至重新恢復服務之最大可容忍中斷時間要求。
■ 識別資通系統使用之第三方軟體、服務、函式庫或其他元件。
請針對⑴⑵⑶逐一說明：為何廠商的說法不足以取代該控制措施？機關應如何驗證廠商確實落實該項防護基準要求，並要求驗收時提供怎樣的客觀佐證？（30 分）

**網友主解摘要與查核**：MoAI 逐項說明廠商說法為何不足、如何驗證、驗收佐證，架構完整，選為主解；但其引「《資通安全管理法》第 10 條」說明委外，條次未經查證，作答宜改引「資通安全管理法及施行細則有關委外監督之規定」或直接引用分級辦法附表的防護基準，不寫無把握的條次。

**整理者補寫**：共通原則：資安責任不因委外移轉，機關須以契約、驗證與持續監督確認廠商落實防護基準，不能以廠商「已具備某機制」取代控制措施本身。

| 廠商說法 | 為何不足 | 機關驗證方法 | 驗收客觀佐證 |
|---|---|---|---|
| ⑴ HTTPS＋帳密即可，不需機關指定控制點 | HTTPS 只保護傳輸、帳密只做身分鑑別，都不限制「從哪裡連」；管理介面若對全網開放，帳密遭竊或暴力破解即可從任何地點登入 | 契約明定遠端管理只能經機關核定的 VPN、跳板機或指定來源 IP，並搭配 MFA；檢視防火牆與安全群組設定；由未授權來源實測連線應被拒；查核管理介面是否暴露於網際網路 | 網路與管理路徑架構圖、控制點與 ACL 設定匯出、負向測試紀錄（截圖、日誌）、跳板機或 VPN 連線紀錄、外部掃描或滲透測試報告 |
| ⑵ 雲端有備份備援，機關不需訂定最大可容忍中斷時間 | 備份備援是手段，可容忍中斷時間是機關依業務衝擊決定的目標，責任在機關；未訂目標就無法驗證廠商的備援是否足夠，也無法寫入 SLA | 機關依 BIA 訂定最大可容忍中斷時間（及 RPO），寫入契約與 SLA；要求廠商提出對應的備援架構、備份頻率與異地／離線保存；辦理實際切換與還原演練並計時 | 核定的 BIA 與 RTO／RPO 文件、SLA 條款、備份排程與成功紀錄、復原演練計畫與結果報告（實測復原時間、資料一致性驗證） |
| ⑶ 元件由廠商管理且常見，不需完整第三方元件清單 | 常見元件正是攻擊者大量利用的目標（如 Log4j）；機關沒有清單就無法在新弱點公告時判斷是否受影響、要求修補期限 | 契約要求提交並持續更新第三方元件清冊（SBOM，含名稱、版本、來源、授權），涵蓋作業系統、函式庫、開源套件與雲端服務；以 SCA 工具或弱點掃描比對清單；約定弱點通報與修補時限 | SBOM 文件（如 SPDX、CycloneDX 格式）、SCA 或弱點掃描報告、修補紀錄、雲端服務清單與版本、廠商弱點通報紀錄 |

另可要求第三方資安檢測、雲端服務的資安認證（如 ISO/IEC 27001、27017）與稽核權條款，並定期稽核。

## 三、零信任設計的驗收測試（20 分）

**阿摩查核**：

- [申論頁 594594](https://yamol.tw/exam/145847?info=essay.594594)：MoAI - 您的AI助手，2026-10-07，詳解 7552789，標示由 MiniMax-M3 產生，付費，已解鎖查核，有幫助 0／沒幫助 0

**題目**：三、某機關將公文系統建置於雲端環境，承辦人員可使用機關配發筆電於機關外部透過 Internet 存取系統。本系統已完成下列七項零信任（Zero Trust）設計：
■ Identity（身分）採機關集中式身分管理及 MFA，使用者須完成帳號密碼及第二因素驗證後，才能建立有效 Session。
■ Device（裝置）僅允許已註冊、受機關 MDM 管理且符合安全基準之裝置存取，裝置狀態不合規時應拒絕存取。
■ Application（應用程式）登入後仍依使用者角色進行功能及 API 授權，一般承辦人不得使用管理功能。
■ Network（網路）外部連線須經 ZTNA Gateway，後端服務不得直接由 Internet 存取；內部服務間亦須進行身分驗證。
■ Data（資料）公文依業務單位及案件承辦關係進行資料層級授權，使用者只能取得其業務需要之資料。
■ Least Privilege（最小權限）承辦人僅具有查詢、編輯等職務必要權限，不具有其他非必要權限。
■ Continuous Verification（持續驗證）系統持續評估使用者、裝置及存取行為；風險狀態重大變化時，應重新判斷是否繼續提供服務。
機關驗收人員提出下列測試方式：
1.檢查登入畫面是否顯示第二因素驗證。
2.檢查裝置管理平台是否有記錄承辦人員筆電。
3.檢查角色權限設定表是否存在。
4.檢查防火牆是否設定來源限制。
5.檢查資料庫是否存在資料權限欄位。
6.檢查角色是否具有最小權限。
7.檢查系統是否設定定時重新登入。
上述驗收方式其實不足以證明對應控制已有效實作，請自選其中 4 項說明：原驗收方式的「問題」及應有的「正確測試方式」？（20 分）

**網友主解摘要與查核**：MoAI 選第 1、2、4、7 項，指出原方法只檢查「設定或介面存在」而未測試「控制在執行時有效」，並提出負向測試與日誌勾稽，正確，選為主解。

**整理者補寫**（任選四項；以下列出七項供選擇）：

| 項目 | 原驗收方式的問題 | 正確測試方式 |
|---|---|---|
| 1. 身分 MFA | 畫面有第二因素欄位不代表後端強制；可能有 API 或舊入口繞過 | 以正確密碼、錯誤或略過第二因素嘗試登入與呼叫 API，確認無法取得有效 Session；測試所有入口；檢查 IdP 日誌 |
| 2. 裝置合規 | 平台有登錄筆電不代表會拒絕不合規裝置 | 以未註冊裝置、及刻意使已註冊裝置不合規（關閉防毒、缺修補）嘗試存取，應被拒絕或降權；查政策決策日誌 |
| 3. 應用授權 | 權限設定表存在不代表程式確實檢查 | 以一般承辦人帳號直接呼叫管理功能 URL 與 API、竄改參數，應回 403；做授權測試與滲透測試 |
| 4. 網路 ZTNA | 防火牆有來源限制不代表後端無法直連；也未驗證服務間鑑別 | 從 Internet 直接連後端服務位址、繞過 ZTNA 閘道應失敗；在內網以未鑑別服務身分呼叫其他服務應被拒；外部掃描確認無暴露 |
| 5. 資料層授權 | 有權限欄位不代表查詢時被套用 | 以承辦人 A 嘗試讀取非承辦案件（改案件 ID、批次匯出），應被拒；檢查回傳筆數與日誌 |
| 6. 最小權限 | 只看角色名稱無法證明權限未過大 | 匯出每個角色的實際權限清單逐項比對職務需求；以帳號實測不必要功能；檢查是否有共用或殘留特權帳號 |
| 7. 持續驗證 | 定時重新登入是固定週期，不是依風險動態判斷 | 模擬風險變化（異地登入、裝置變為不合規、異常大量下載），確認系統即時要求再驗證或中斷 Session；檢視風險評分與決策日誌 |

驗收應以「正向＋負向測試＋日誌佐證」證明控制在執行時有效，而非只確認設定存在。

## 四、機關內部利用民眾個資（每小題 10 分，共 20 分）

**題組敘述**：民眾服務系統保存姓名、身分證字號、聯絡方式與申辦案件資料；某業務單位主張其他單位有業務需要即可直接查詢使用。

### （一）上述說法是否適當

**阿摩查核**：

- [申論頁 594595](https://yamol.tw/exam/145847?info=essay.594595)：MoAI - 您的AI助手，2026-10-07，詳解 7552775，標示由 MiniMax-M3 產生，付費，已解鎖查核，有幫助 0／沒幫助 0

**題目**：(一)上述說法是否適當？請說明理由。

**網友主解摘要與查核**：MoAI 指出不適當，援引個資法第 5、16、18 條的目的拘束、必要性與安全維護，正確，選為主解。

**整理者補寫**：不適當。

1. **目的拘束**：個資法第 5 條要求蒐集、處理、利用不得逾越特定目的之必要範圍，並應與蒐集目的具正當合理關聯；資料「已在機關資料庫」不代表全機關可任意使用。
2. **公務機關利用要件**：第 16 條規定公務機關利用個資應於執行法定職務必要範圍內，並與蒐集之特定目的相符；特定目的外利用須符合但書情形之一（法律明文規定、維護國家安全或增進公共利益所必要、免除當事人生命身體自由財產危險、防止他人權益重大危害、公共利益統計或學術研究且無從識別、有利於當事人權益、經當事人同意）。
3. **最小必要與安全維護**：即使合法，也只能使用必要欄位與範圍；第 18 條要求公務機關指定專人辦理安全維護，防止個資被不當存取。
4. **機關內部各單位有不同職掌**，跨單位利用仍是一次新的「利用」行為，須逐案判斷並留存紀錄。

**網友主解摘要與查核**：MoAI 列法律依據與目的、最小化、身分與權限、安全維護、稽核紀錄等，完整，選為主解。

**整理者補寫**：

1. **適法性**：需求單位以書面說明法定職務依據、使用目的、所需欄位、期間與使用人員；確認符合原蒐集特定目的，或屬第 16 條但書的目的外利用事由，並經權責主管或個資保護窗口核准。
2. **最小必要**：只開放必要欄位與查詢條件，其他欄位遮罩（如身分證字號部分隱碼），能用去識別化或統計資料就不提供個別資料；限制匯出、列印與批次查詢。
3. **帳號與權限**：個人帳號、MFA、依角色與案件關係授權（RBAC／ABAC），設定權限期限並定期複核，離調職即停用。
4. **安全措施**：加密傳輸與儲存、網段與系統存取控制、異常查詢（大量、非上班時間）告警。
5. **紀錄與稽核**：保存查詢者、時間、對象、目的的存取紀錄並防竄改，定期稽核比對申請目的。
6. **程序與告知**：更新個人資料檔案的公開項目或告知內容（如有新增利用目的），人員完成個資保護教育訓練並簽署保密責任。
